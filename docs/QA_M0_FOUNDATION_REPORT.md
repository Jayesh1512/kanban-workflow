## Additional independent regression coverage

The architect tests already cover the normal lifecycle, later-module failure, initial schema constraints, basic tombstone/checkpoint storage, and forwarding. QA adds only the previously uncovered boundaries:

- `tests/qa-m0-lifecycle.test.ts` (three tests): failure in the first register still closes a constructed dependent that never registered; failure in the first start closes a dependent that never started and repeated close does not duplicate cleanup; dependent stop failure still releases platform and surfaces an aggregate failure. These run real foundation lifecycle code with explicit synthetic module probes, not Telegram/DB worker implementations.
- `tests/qa-m0-persistence.test.ts` (five tests): applies the actual migration to a new temporary disk-backed PGlite directory, inserts synthetic records, closes the engine and reopens the same database before assertions. Verifies singleton account retention/duplicate rejection; scoped and null-scope pre-message tombstones and NULLS NOT DISTINCT uniqueness; separate history/live positions and generations; source sender/peer/forward snapshots with hidden origin still null and unchanged body; retained extraction/provenance/input hash with absent Jev decision; date-only fact with explicit external actor and manual lifecycle source; sourced contact roles and role-bearing read/create types; and one active mutation per ticket even across distinct proposals with an ambiguous remote outcome. A completed predecessor releases that journal slot. Direct SQL journal writes never move the ticket.
- The tests also exercise actual runtime date/fact validators to reject an invented instant for a date-only commitment. They do not claim a date-inference model resolved the text, that a role was correctly inferred, that singleton account rows implement the bind-account service, that storing a tombstone implements anti-resurrection logic, or that a schema journal write executed remote approval/application.

PGlite runs the migration's PostgreSQL SQL engine in process and persists to its own temporary directory. It is **not Docker PostgreSQL**, a deployment/migration runner/advisory-lock test, or a substitute for M1 Compose/PostgreSQL restarts.
